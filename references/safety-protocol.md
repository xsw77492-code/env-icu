# 安全协议 (Safety Protocol)

本文件是 env-icu 的**强制闸门**。任何修复动作执行前必须逐条通过；违反即视为排障失败——即使问题"修好了"。

排障目标不只是修好环境，而是**绝不让它更坏**。环境问题最深的伤害往往来自"修"这个动作本身。

## 一、禁止清单（不可协商）

| # | 禁止操作 | 原因 | 替代方案 |
|---|---|---|---|
| 1 | 盲目 `pip install --upgrade`（全量升级） | 升级一个有问题时，全量升级引入 N 个新问题；破坏版本锁定 | 只升级目标包，指定版本；升级前 `pip freeze` 备份 |
| 2 | `sudo pip install` / 管理员权限装包到系统 Python | 污染系统 Python，可能破坏 OS 组件依赖 | 新建 venv；`--user` 安装（纯 Python 包场景） |
| 3 | `--force-reinstall` / `--ignore-installed` 大范围覆盖 | 绕过依赖解析，制造隐性冲突 | `--dry-run` 预演后精确重装；必要时重建环境 |
| 4 | 删除 / 覆盖系统 Python 或任何非本项目的解释器 | 破坏面不可控 | 只操作项目级 venv |
| 5 | 修改系统级文件（`/usr/lib`、系统 PATH 永久变更、`/etc` 配置） | 影响范围超出本次排障 | 优先环境级/项目级方案；必须系统级时先向用户说明并确认 |
| 6 | 关闭安全校验（`--trusted-host` / 禁用 SSL 验证）作为持久方案 | 供应链安全降级 | 先修网络/证书链；临时使用必须向用户明示风险 |
| 7 | 在用户未确认的情况下执行任何写操作（装/卸/改配置） | 环境是用户的生产工具 | 先给出计划，获得确认后再动手 |
| 8 | 混合 conda 与 pip 安装同一批底层包（如 numpy） | 两套包管理器互相覆盖，制造"幽灵冲突" | 一个环境只用一种主管理器；混用必须明确哪个主导、哪个补缺 |

## 二、动手前四问（每次修复前自检）

1. **有证据吗？** 根因是否由体检报告支撑，而不是猜测？
2. **有备份吗？** 修改前是否已保存环境状态？
   ```bash
   python -m pip freeze > requirements.backup.$(date +%Y%m%d%H%M).txt
   # Windows PowerShell: python -m pip freeze > requirements.backup.txt
   ```
3. **影响面多大？** 该操作是否只影响当前项目环境？会不会触碰系统 Python / 用户数据？
4. **可回滚吗？** 如果这一步失败，回滚命令是什么？能否说出具体的回滚步骤？

四问中任何一问答不上来 → 停下，先补齐。

## 三、修复纪律

- **一次只改一个变量**：同时执行两个修复动作，失败后无法定位是哪个的问题
- **每一步都验证**：改完立即跑验证命令，通过才进入下一步
- **失败即回滚，不叠加**：验证失败时回滚当前步，回到证据重新判断；禁止"这个不行再试试那个"式的连招
- **修复范围最小化**：能用补装解决的，不重建；能重建 venv 解决的，不动系统

## 四、危险的"常识"（老教程的坑）

以下建议在老教程里流传甚广，属于高风险操作，本技能包明确禁止直接执行：

- `sudo pip install --upgrade pip`（升级系统 pip 会连带破坏系统包管理）
- `pip install --upgrade setuptools wheel` 无脑执行（部分老项目依赖旧版 setuptools 行为）
- `chmod -R 777 /usr/lib/python*` 类权限暴力修复
- 直接 `rm -rf` site-packages 里的报错包（残留元数据会导致后续 pip 状态错乱；应使用 `pip uninstall`）
- 复制网上"一行修复脚本"直接执行（先读懂，再决定）

## 五、升级为"重建"的判断标准

满足任一条件，应建议用户**重建环境**而不是继续修复：

- 同一环境本周内出现过 3 次以上互相矛盾的包状态
- `pip check` 输出超过 5 条矛盾且无法收敛
- 环境来源不明（不知道当初怎么装的）
- 修复成本明显高于重建（缺 `requirements.txt` 时先尝试导出）

重建步骤（标准流程）：

```bash
python -m pip freeze > requirements.old.txt      # 尽力导出旧状态
python -m venv .venv-new                          # 全新环境
.venv-new/Scripts/activate                        # POSIX: source .venv-new/bin/activate
python -m pip install -r requirements.old.txt     # 逐条核对重装
```

旧环境保留到用户确认新环境可用后再删除。
